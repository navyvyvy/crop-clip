# 방송 재생이 녹화 시작 시 끊기는 현상 (2026-10-27)

상태: 합성 영상의 Chromium·Edge 검사에서 시작 끊김 완화를 확인했다. 사용자가 선택한 빠른 MP4 변환을 유지하도록 기존 H.264 코덱과 비트레이트는 유지했다. 실제 방송 장시간 검증과 브라우저·드라이버 환경별 확인은 남아 있다.

## 관찰

새 브라우저에서 이미 생성한 1920×1080/30fps 영상 파일을 재생하고, 녹화를 시작하기 전후의 requestVideoFrameCallback 간격을 측정했다. 측정 브라우저에서 테스트 영상을 먼저 인코딩하지 않도록 해 첫 인코더 초기화 비용이 가려지지 않게 했다.

- 기존 H.264: 첫 시작의 프레임 공백 350ms, 후속 시작 420ms/360ms. 녹화 전에는 최대 약 40~50ms였다.
- VP8 비교: Chromium 첫 시작 140ms, Edge 130ms. 후속 측정도 각각 80~160ms, 50~120ms였다. WebM의 VP8 전환은 빠른 MP4 변환을 유지하지 못하므로 채택하지 않았다.
- H.264 유지 비교의 첫 시작 공백: 소프트웨어 캔버스 320ms, 원본 캡처/오디오를 제외한 진단 240ms, WebCodecs 예열 370ms, 작은 MediaRecorder 예열 340ms, 영상 프레임에 맞춘 그리기 210ms, 명시적 H.264 프로필 290ms, 프로필+프레임 동기화 260ms. 모두 첫 시작 200ms 미만 기준을 통과하지 못했다.
- MediaRecorder.start()의 동기 호출 자체는 대부분 1ms 이내였지만 실제 start 이벤트는 약 300~400ms 뒤에 도착했다. 코덱 변경 비교를 함께 보면 H.264 녹화 파이프라인 시작과 관련된 경합이 유력하다. GPU/드라이버의 구체적인 내부 원인을 확정한 것은 아니다.

위 수치는 서로 다른 브라우저 실행의 관찰값이며 통계적으로 보장하는 개선율이 아니다. 합성 파일은 반복 재생되므로 실제 라이브 방송의 스트림·디코더·드라이버 환경과도 차이가 있다. 프레임 동기화만 사용하는 방식은 배경 탭 동작도 별도로 검증해야 한다.

## 적용한 변경과 최종 측정

src/content/frame_capture.ts에서 영상의 VideoFrame을 먼저 받은 뒤, 필요한 영역은 VideoFrame 복제로 지정해 생성 트랙에 전달한다. HTML 영상에서 프레임을 생성할 때 영역·크기를 한꺼번에 지정한 중간 구현은 Chromium에서 300~450ms 공백이 다시 나와 제외했다.

| 브라우저·모드 | 첫 시작 최대 공백 | 후속 시작 최대 공백 |
| --- | --- | --- |
| Chromium 전체 | 160ms | 120ms / 100ms |
| Chromium 영역 | 120ms | 120ms / 100ms |
| Edge 전체 | 120ms | 120ms / 110ms |
| Edge 영역 | 160ms | 120ms / 130ms |

- H.264 코덱·비트레이트와 기존 녹화 형식 선택은 유지했다. WebM에서 MP4로 변환할 때 실시간 MediaRecorder 재인코딩이 발생하지 않고 결과가 재생되는지 검사했다.
- 영상의 네 구역에 서로 다른 색을 넣어, 전체 녹화와 선택 영역의 실제 픽셀 및 출력 크기가 맞는지 검사했다. 저장된 음성과 마지막 구간 탐색, 전체·선택 구간의 2·3·4분할 검사도 통과했다.
- 대기 중인 프레임은 한 개로 제한한다. 종료·취소 시 프레임, 생성 트랙, 스트림 writer를 해제하고, 프레임 전달 오류는 기존 녹화 오류 복구 경로로 보낸다.
- 다중 영역과 미지원 브라우저는 기존 캔버스 경로를 사용한다. 픽셀 정렬이나 레터박스 때문에 직접 프레임 전달이 불가능한 경우도 정확한 구도를 유지하도록 캔버스로 그린다. 따라서 모든 구도·브라우저에서 같은 개선 폭을 보장하지 않는다.
- 최종 변경의 전체 단위 검사가 통과했다. 브라우저 전체 검사 8개를 통과한 뒤 프레임 복제 방식 보완에 해당하는 녹화·영역·음성·분할·복구 검사를 재실행했다. Chromium과 Edge 모두 출력 크기·색상·음성 및 실시간 재인코딩 없는 MP4 변환 검사를 통과했다.
- Chromium 전체·영역 녹화 종료 24회: 회차별 GC 후 열린 프레임·생성 트랙·인코더·캔버스·변환 워커 잔존 수 0. 워밍업 이후 JS 힙 증가는 254,704바이트였다. 브라우저 전체 프로세스의 private memory는 약 702~831MiB 범위로 증가·감소하다 마지막에 748MiB였으며, 반복 횟수에 비례하는 지속 증가는 관찰되지 않았다.
- Edge 시작·취소 16회: 4회 단위 검사에서 위 자원 잔존 수 모두 0, 최종 IndexedDB recordings/parts/chunks 모두 0개였다. 프로세스 private memory는 약 567~578MiB였다. 두 반복 검사에서 재사용하는 비활성 원본 오디오 트랙 1개는 의도적으로 유지됐다.

VideoFrame의 영역 복제는 [WebCodecs 명세](https://www.w3.org/TR/webcodecs/#videoframe-interface)에 따른다. 생성 트랙 API는 [Chrome의 insertable streams 문서](https://developer.chrome.com/docs/capabilities/web-apis/mediastreamtrack-insertable-media-processing)에 설명되어 있으며, 기능 검출과 기존 경로를 함께 유지했다.

## 재현

### Linux CI의 MP4 영역 녹화 호환성 보완

Windows 검사 이후 Linux CI에서 MP4 영역 녹화를 시작할 때 Chromium 렌더러가 SIGSEGV로 충돌했다. 원본 코드로 전체 검사 두 번과 해당 검사만 실행한 한 번에서 같은 지점이 실패했다. Windows의 해당 검사 세 번은 모두 통과해 로컬 통과만으로 확인할 수 없었던 환경 차이다.

MP4에서는 잘라낸 native VideoFrame 대신 캔버스로 영역 픽셀을 만든 뒤 생성 트랙에 전달하도록 바꿨다. 이 변경 후 Linux CI의 같은 회귀 검사가 통과했다. 전체 화면과 WebM의 직접 프레임 전달, H.264 코덱과 빠른 MP4 변환은 유지한다. MP4 영역 녹화에는 캔버스 처리 비용이 남으며, Chromium 내부 충돌의 정확한 원인까지 확정한 것은 아니다.

단위 검사에는 MP4 영역만 캔버스를 사용하고 자르지 않는 MP4는 직접 전달하는지 확인하는 항목을 추가했다. 기존 브라우저 회귀 검사는 생략하거나 제한 시간을 늘리지 않았다.

### 시작 지연 측정

먼저 기존 recording-profile.spec.mjs를 실행해 테스트 영상 캐시를 생성한다. 이후 새 브라우저로 진단 검사를 실행한다.

```powershell
$env:CROPCLIP_PROFILE_REPORT = 'node_modules/.cache/startup-source-profile.json'
npx playwright test recording-profile.spec.mjs
Remove-Item Env:CROPCLIP_PROFILE_REPORT
$env:CROPCLIP_STARTUP_REPORT = 'node_modules/.cache/startup-report.json'
npx playwright test recording-startup.spec.mjs
```

현재 진단은 명시적으로 실행할 때 첫 시작의 100ms 이상 공백을 실패로 보고한다. 일반 브라우저 검사에서는 건너뛴다. 녹화 형식과 원본 옵션을 바꿔 비교하는 방법은 [녹화 저장 검증 및 인계](recording-handoff.md#녹화-시작)에 있다.

비교 실험 원본은 Git에서 제외된 node_modules/.cache/cropclip-startup-*.json에 있다. 임시 코덱 변경, 예열, 캔버스와 타이머 교체 코드는 제거했다.

최종 시작 측정은 cropclip-startup-clone-*.json, 24회 녹화/16회 취소 결과는 cropclip-native-frame-profile-24-chromium.json 및 cropclip-native-frame-cancel-final-edge.json에 있다. 이 검사는 OS/GPU 누수 부재나 실제 방송의 모든 부하 조건을 보장하지 않는다.

## 0.4.1 재현

같은 1080p·30fps 소스로 Chromium에서 원본 옵션을 끄고 켠 경우를 각각 세 번 재현했다. 일반 녹화의 첫 표시 간격은 130ms, 원본 조회와 함께 시작한 화면 녹화는 120ms였다. 각 실행의 첫 녹화 전 표시 간격은 약 40ms였다. 두 실행 모두 첫 녹화에서 100ms 진단 기준을 넘었다.

Chromium 추적에서 8Mbps H.264 하드웨어 인코더 초기화에 188~240ms가 걸렸다. 같은 구간에 재생 탭의 미디어 스레드가 기다렸고 녹화기의 영상 읽기 요청도 겹쳤다. 플레이어의 `captureStream()` 영상 트랙을 직접 넘겨도 녹화기의 GPU 읽기가 매 프레임 남았다.

별도 렌더러에서 MP4를 기록한 실험에서는 Chromium의 화면 표시 간격이 약 40ms였지만, 약 5초간 전달하려던 영상 프레임 중 42개가 건너뛰어졌다. 방송 표시 간격과 저장 파일의 영상·음성 연속성을 함께 통과해야 경로를 교체할 수 있다.

워커에서 소프트웨어 H.264 인코더를 합성 프레임 한 장으로 준비한 뒤 실제 프레임을 복사하고 인코딩하도록 했다. 준비 과정의 프레임은 파일에 들어가지 않는다. `dist-software`에만 들어가는 1080p·30fps 전체 녹화 경로다. Chromium의 같은 시작 검사에서 원본 옵션을 끈 경우 70ms, 켠 경우 60ms로 줄었다.

45초 샘플로 33초 녹화를 실행했다. Edge MP4의 시작 화면 간격은 최대 100ms였으며 보정 후 저장 영상의 최대 간격은 55ms였다. Chromium WebM의 시작 화면 간격은 40ms였고 저장 영상의 최대 간격은 55ms였다. 두 파일의 영상과 음성 시작 차이는 21ms 이내였다. Chromium에서 시험 경로의 WebM을 두 MP4로 빠르게 나눴고, 스트림 복사와 두 파일의 재생을 확인했다. 실제 치지직 라이브, 다른 해상도, 60fps, H.265에서 같은 개선이 확인되기 전에는 시험 경로를 기본 배포에 적용하지 않는다.

### 저장된 WebM의 첫 10초 검사

같은 1080p·30fps 샘플을 8Mbps 설정으로 33초 녹화했다. 다운로드한 파일을 처음부터 끝까지 디코딩하면서 첫 10초를 초 단위로 나눠 검사했다.

| 브라우저와 녹화 방식 | 첫 10초 최대 프레임 간격 | 파일 전체 최대 프레임 간격 |
| --- | ---: | ---: |
| Edge 일반 녹화, 원본 OFF | 55ms | 55ms |
| Edge 일반 녹화, 원본 조회를 5초 뒤 실패시킨 경우 | 52ms | 52ms |
| Chromium 일반 녹화, 원본 OFF, 2회 | 42~50ms | 50~136ms |
| Chromium 워커 시험 빌드, 원본 OFF | 34ms | 55ms |

Edge에서 조회 실패 뒤 첫 저장 작업은 녹화 시작 5.04초에 실행됐다. 그 구간의 저장 영상에서 프레임 간격은 최대 41ms였다. Chromium 일반 녹화에서는 초반 구간 보정이 적용됐다. 136ms 공백은 첫 실행의 저장 파일에서 10초 이후에 관찰됐으며, 재검사에서는 최대 50ms였다. 이 비교는 Windows 로컬 샘플에서 수행했다.

### 일반 녹화 버전 비교

Chromium에서 같은 1080p·30fps 영상으로 원본 옵션을 끄고 33초씩 녹화했다. 표의 간격은 다운로드한 파일에서 측정했다.

| 빌드 | 첫 10초 최대 프레임 간격 | 파일 전체 최대 프레임 간격 |
| --- | ---: | ---: |
| v0.3.13 | 79ms | 79ms |
| 원본 저장 도입 커밋 `fcf80b2` | 80ms | 119ms |
| v0.4.0 | 67ms | 67ms |
| v0.4.1 | 80ms | 80ms |

v0.3.13과 `fcf80b2`는 기존 초반 보정으로 파일이 각각 약 2.1초 짧아져 길이 검사가 실패했다. 이 비교에서는 원본 저장을 추가한 시점부터 프레임 공백이 계속 증가하는 흐름이 나타나지 않았다.

`fcf80b2`는 원본 옵션을 켰을 때만 조회했고 일반 녹화의 프레임 수집 주기는 유지했다. `93e09a6`은 해당 코드를 녹화 컨트롤러로 옮겼다. `ee40a01`은 재생 프레임 알림을 사용하기 시작하면서 보조 캡처가 30fps 기준 약 67ms 이상 알림을 기다리게 했다. 다음 타이머 실행까지 겹치면 영상이 계속 재생돼도 저장 파일에서 프레임이 빠질 수 있었다. v0.4.1에서 녹화 5~9초 동안 알림만 지연시키자 두 실행에서 최대 95ms, 91ms 공백이 재현됐다.

v0.4.2에서는 30fps 기준 약 42ms가 지나면 기존 보조 타이머가 이어받는다. 첫 수정본의 지연 검사에서 Chromium 3회의 최대 간격은 68·70·75ms, Edge 2회는 66·72ms였다. 검사 기준은 85ms 미만이며 결과 파일을 끝까지 디코딩해 화면 멈춤도 확인한다.

첫 수정본은 타이머 프레임 직후 도착한 재생 알림을 중복으로 간주했다. 전체 릴리스 검사에서는 이 조건 때문에 실제 시작 프레임 30개 중 1개가 빠졌다. 재생 알림은 미디어 시간으로만 판단하고, 보조 타이머에 최근 캡처와의 간격 제한을 적용하도록 고쳤다.

수정 후 원본 OFF에서 같은 1080p·30fps 영상을 33초씩 녹화했다. 다운로드한 파일의 첫 10초와 전체 최대 프레임 간격은 Chromium 50ms, Edge 51ms였고 두 파일 모두 정지 화면이 검출되지 않았다.

MP4 연속성 검사 한 번에서 음성이 영상보다 987ms 늦게 끝났다. 같은 검사에서 v0.4.1은 7ms, v0.4.2 재검사 두 번은 2·5ms였으며 최초 차이의 원인은 확인되지 않았다.

전체 릴리스 검사를 통과한 ZIP을 다시 풀어 시작 30프레임과 WebM 알림 지연을 각각 세 번 확인했다. 시작 프레임은 매번 30개가 잡혔다. 알림 지연 검사 중 하나는 저장 파일 9.14초에서 최대 간격이 85ms여서 실패했다. 원본 OFF 1080p·33초 일반 WebM 세 파일의 최대 간격은 Chromium 50·50ms, Edge 67ms였으며 모든 파일을 끝까지 디코딩했다.

마지막 재생 알림으로부터 한 프레임 간격이 지나면 보조 타이머가 이어받도록 대기 시간을 줄였다. 가짜 시계로 다음 알림 없이 36ms가 흐른 경우를 재현해 이전 동작에서 실패하고 수정 후 통과하는 것을 확인했다. 수정본에서 시작 30프레임은 3회 모두 잡혔고, 알림 지연 파일의 최대 간격은 78·62·76ms였다.

같은 수정본의 ZIP을 풀어 원본 OFF 1080p·33초 WebM을 Chromium 두 번, Edge 한 번 저장했다. 첫 10초의 최대 프레임 간격은 47·53·60ms, 파일 전체는 52·53·60ms였다. 세 파일 모두 화면 멈춤이 검출되지 않았고 영상과 음성의 종료 시각 차이는 17~25ms였다.

### WebM 초반 보정의 화질

원본 저장을 끄고 같은 1080p·30fps 샘플을 v0.3.13 WebM, v0.4.2 WebM·MP4에서 목표 8Mbps로 녹화했다. 세 경우 모두 녹화기의 목표값은 8Mbps였다. 다운로드본의 디코딩 프레임은 녹화기에서 받은 데이터의 프레임과 모두 일치했다. 비교한 프레임 수는 각각 176·237·237개다.

초반 보정 지점 근처에 키프레임이 없는 별도 1080p WebM에서는 다운로드 파일을 다시 인코딩하는 경로가 실행됐다. 같은 8Mbps 목표로 인코더의 `veryfast` 프리셋을 적용했다. 양쪽 결과는 같은 시작 위치와 141개 프레임을 가졌고, 같은 위치의 표본 18프레임에서 밝기 PSNR 중앙값은 44.29dB에서 46.21dB로 개선됐다. 일반 저장과 키프레임 경계에서 가능한 초반 보정에는 패킷 복사를 사용한다.
