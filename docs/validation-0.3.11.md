# 0.3.11 개발 버전 검증

검증일: 2026-09-30. 비교 대상은 v0.3.10 태그(`dc899bb`)와 파일 분리·복구 수정을 포함한 현재 0.3.11 작업본입니다.

검사한 경로에서 새 기능 회귀나 반복 횟수에 따른 자원 누적은 재현되지 않았습니다. 다만 아래 측정은 짧은 합성 영상 검사이므로 실제 방송에서의 장시간 안정성이나 모든 기능의 동등성을 보증하지 않습니다.

## 기능과 코드 검사

확인된 실행 결과:

- 현재 버전 `npm run check`: 빌드·타입·단위 검사 통과, Chromium 브라우저 검사 6개 통과. 별도 실행용 성능 측정 1개는 정상적으로 건너뛰었습니다.
- v0.3.10 Chromium: 동일한 MP4 녹화·분할·배속·GIF·PNG 검사 1개 통과.
- 현재 버전 Edge: MP4·분할·변환 검사와 실제 녹화·미니 플레이어 이동·WebM 분할·저장 오류 복구 검사 2개 통과.
- 빌드 ZIP의 39개 파일이 dist의 원본과 SHA-256 기준으로 일치했습니다. `git diff --check`도 통과했습니다.

검사 범위:

- 빌드·타입 검사, 상태 정규화, 합성 배치, 시간 범위·분할, 단축키·지연 입력, 녹화·변환 자원 정리 검사를 실행합니다.
- 저장 실패 시 완성된 연속 구간 복구, 복구 실패 시 원본 보존과 재시도, 명시적 취소 시 삭제, 결과창 중복 방지를 검사합니다. 이 오류 처리 동작은 이전 버전에서 의도적으로 개선한 부분입니다.
- 브라우저에서 전체·영역 녹화, 미니 플레이어 전환, 선택 테두리, 시작 준비 중 정지·취소, 설정 복구를 확인합니다.
- 실제로 생성한 WebM 영상의 전체·선택 구간 2·3·4분할과 생성 파일의 재생을 검사합니다.
- MP4 녹화, MP4·WebM 2분할 파일 재생, 2배속 출력의 재생 시간을 검사합니다. GIF·장면 PNG 저장은 파일 시그니처를 확인하며 모든 프레임의 화질 검사는 아닙니다.
- 분리 전후 함수와 호출부를 비교했습니다. 저장 데이터 형식, 기본 설정, 화면 구조는 유지하며, 합성 배치는 고정 시드 입력 1,000개에서 이전 계산과 일치했습니다.

## 반복 녹화 비교

두 버전에 동일한 1920×1080, 30fps 합성 WebM 파일을 공급했습니다. 전체·영역 녹화를 번갈아 3초씩 실행하고 결과를 재생한 뒤 닫았습니다. Chromium은 버전별 16회, 설치된 Edge는 버전별 8회로 총 48회입니다. Chromium은 실행 순서를 바꿔 한 번 더 측정했습니다. 브라우저는 별도 프로필의 headless 환경입니다.

시간은 중앙값입니다. 시작은 키 입력 직전부터 MediaRecorder 시작까지, 종료는 정지 입력부터 결과창 분할 버튼 활성화까지입니다. 렌더러 작업 시간은 녹화 구간의 CDP TaskDuration 차이로, 전체 프로세스 CPU 사용률은 아닙니다.

| 지표 | Chromium 0.3.10 | Chromium 0.3.11 | Edge 0.3.10 | Edge 0.3.11 |
| --- | ---: | ---: | ---: | ---: |
| 녹화 시작 (ms) | 25.25 | 35.25 | 24.55 | 25.90 |
| 종료→결과 준비 (ms) | 515.37 | 317.84 | 555.64 | 534.13 |
| 렌더러 작업 시간 (초) | 0.415 | 0.426 | 0.372 | 0.365 |
| 원본 재생 드롭/전체 프레임 | 47/1405 | 41/1419 | 14/709 | 23/703 |
| GC 후 최대 JS 힙 (MiB) | 2.966 | 2.970 | 2.914 | 2.874 |
| 브라우저 프로세스 private memory 최대 합계 (MiB) | 898.8 | 887.4 | 881.1 | 894.9 |

Chromium은 시작이 10ms, 렌더러 작업 시간이 약 2.9% 늘었습니다. Edge는 재생 드롭이 9프레임 늘었습니다. 반대로 종료 대기 시간과 일부 지표는 줄었습니다. 단기 측정 편차가 있고 프레임 수가 적으므로 이 차이만으로 개선이나 회귀의 원인을 확정하지 않습니다. 원본 재생의 드롭 수는 저장된 파일의 누락 프레임 수를 직접 측정한 값이 아닙니다.

모든 사이클에서 다음을 확인했습니다.

- 원본 캡처는 한 번 생성하여 재사용했습니다. 녹화용 캔버스·복제 트랙은 종료 후 살아 있지 않았습니다.
- 다음 녹화에 재사용하는 원본 오디오 트랙 1개는 비활성 상태로 유지됩니다. 모든 캡처 자원을 매번 없애는 구조는 아닙니다.
- 결과창을 닫은 뒤 전용 worker는 0개였습니다. 이 측정은 녹화·결과창 반복이며 장시간 변환 반복 부하 검사는 아닙니다.
- GC 후 JS 힙은 두 버전 모두 약 3MiB였고, 두 번째에서 마지막 사이클까지 증가는 약 0.13MiB였습니다. DOM·이벤트 리스너의 반복 누적은 관찰되지 않았습니다.
- 브라우저 프로세스 private memory는 증가와 감소를 반복했습니다. 최대값만으로 누수 여부를 판정하지 않았습니다.

실제 치지직 네트워크 버퍼링, 몇 시간 연속 사용, 복잡한 영상의 인코딩 부하, GPU 메모리는 미검증입니다. GC 측정은 테스트 페이지 렌더러 기준이며 브라우저 전체의 JS 힙을 합산한 값이 아닙니다.

## 추가 메모리·성능 코드 점검

녹화 종료·취소·오류의 타이머·트랙·캔버스 해제, 체크포인트 대기열과 서비스 워커 작업 Map 정리, 플레이어 제거 감시자, 결과창의 임시 비디오·Blob URL·FFmpeg 수명을 재검토했습니다.

빠른 변환 실패 후 실시간 변환으로 넘어갈 때 FFmpeg가 최종 작업 종료까지 남는 경로를 확인했습니다. 실시간 변환은 선택 구간만큼 오래 걸릴 수 있으므로 전환 전에 FFmpeg를 종료하도록 수정했습니다. 무한 누적 누수가 아니라 필요 없어진 엔진을 오래 유지하는 문제입니다. `node scripts/check-ffmpeg-lifecycle.mjs`에 추가한 검사는 수정 전 실패하고 수정 후 통과했습니다.

브라우저 검사에도 반복 분할·변환 뒤 작업자 0개, 임시 비디오 제거, Blob URL 수 복귀를 확인하는 조건을 추가했습니다. 빠른 변환 실패를 주입하는 검사는 실제 FFmpeg 로딩과 실제 MediaRecorder를 사용하며, 실시간 변환이 아직 진행 중인 시점에 FFmpeg 작업자가 사라지는지를 확인합니다.

추가 검증에서 빌드·단위 검사는 통과했습니다. 최초 MP4 브라우저 검사는 테스트의 오류 주입이 적용되지 않아 실패했으며, 실제 작업자에 잘못된 코덱을 전달하도록 테스트를 고친 뒤 Chromium에서 통과했습니다. 나머지 Chromium 검사 5개도 통과했습니다. Edge에서도 MP4·변환 실패 전환 검사와 실제 녹화·반복 분할·저장 오류 복구 검사 2개가 통과했습니다.

이 점검에서는 녹화 프레임 루프나 화질·프레임 설정을 바꾸지 않았습니다. 위 48회 비교 수치는 이 추가 수정 전의 측정값이며, 수정으로 줄어드는 메모리 용량을 MiB 단위로 별도 측정한 것은 아닙니다.

정상 동작에서도 남는 비용은 다음과 같습니다.

- 전체 녹화도 캔버스에 영상을 복사하고 인코딩합니다. 같은 디코딩 프레임의 중복 그리기는 막지만 해상도에 따른 복사·인코딩 비용 자체는 남습니다.
- 체크포인트 전송은 최대 8MiB 조각을 data URL로 직렬화하므로 일시적인 문자열·바이트 복사 비용이 있습니다. 저장 대기량이 64MiB에 도달하면 녹화를 멈추며, 이 값은 프로세스 전체 메모리의 상한은 아닙니다.
- 결과창을 열어 두는 동안 원본과 현재 분할 결과는 다운로드를 위해 유지합니다. 다음 분할·구간 변경 시 이전 분할 결과를 버립니다. 여러 결과창을 열어 두면 각 창의 데이터·미리보기 비용이 함께 남습니다.
- 플레이어 오디오 원본 1개는 비활성 상태로 재사용하고, 플레이어가 영구 제거되면 해제합니다. 썸네일은 최대 24개, 방송 화면의 스크린샷 미리보기는 최대 8개로 제한합니다.

## 시작·취소 반복 점검 (2026-10-02)

정상 저장 종료와 별도로 전체·영역 녹화의 시작 준비 중 취소, 인코더 시작 직후 취소, 체크포인트 생성 뒤 취소를 섞어 검사했습니다. 네 번 연속 취소한 뒤 자원을 측정하며, 각 취소 사이에는 강제 GC를 실행하지 않았습니다. 영상 조건은 위와 같은 합성 1080p·30fps입니다.

수정 전 Chromium 32회, Edge 32회, 추가 Chromium 96회에서 취소한 MediaRecorder·녹화 캔버스는 측정 시 GC로 회수됐고, 활성 녹화 트랙·전용 작업자는 남지 않았습니다. DOM 노드 547개·리스너 57개는 일정했고, 마지막에 IndexedDB의 recordings·parts·chunks가 모두 0개임을 확인했습니다. 재사용하는 비활성 원본 오디오 트랙 1개는 유지됩니다.

| 수정 전 검사 | GC 후 JS 힙 첫→마지막 (MiB) | 프로세스 private memory 첫→마지막 (MiB) |
| --- | ---: | ---: |
| Chromium 32회 | 2.79→3.00 | 670.9→692.4 |
| Edge 32회 | 2.90→3.04 | 612.1→649.7 |
| Chromium 96회 | 2.91→3.24 | 657.8→680.4 |

96회 검사에서는 프로세스 메모리가 약 701.1MiB까지 오른 뒤 668.4MiB까지 내려갔습니다. 이 범위에서 메모리가 단조롭게 누적되지는 않았지만, 증가분 전체를 특정 브라우저 캐시나 GPU에 귀속시킨 측정은 아닙니다. 테스트의 WeakRef 추적 자료와 브라우저 자체 할당도 수치에 포함됩니다. 실제 방송·장시간·GPU 메모리까지 누수가 없다는 결론은 아닙니다.

코드에서 취소 시 `requestData()`로 추가 데이터를 내보내고 곧바로 `stop()`하던 불필요한 요청을 확인했습니다. 취소한 데이터는 저장하지 않으므로 취소 경로의 추가 요청만 제거했습니다. 정상 정지는 기존 요청을 유지합니다. 회귀 검사는 수정 전 추가 요청 1회로 실패했고 수정 후 0회로 통과했습니다. 이 수정으로 위 프로세스 메모리 증가의 원인이 해결됐다고 주장하지 않습니다.

수정 후 빌드·단위 검사와 Chromium의 기존 브라우저 검사 6개가 통과했습니다. 이어 Chromium·Edge에서 각각 32회 취소를 다시 실행해 추가 `requestData()` 호출 0회, 취소한 녹화 객체·캔버스 회수, 활성 녹화 트랙·작업자 없음, 최종 저장 데이터 0개를 확인했습니다.

| 수정 후 검사 | GC 후 JS 힙 첫→마지막 (MiB) | 프로세스 private memory 첫→마지막 (MiB) |
| --- | ---: | ---: |
| Chromium 32회 | 2.90→3.02 | 590.3→680.9 |
| Edge 32회 | 2.92→3.07 | 587.1→608.2 |

수정 후에도 프로세스 메모리는 즉시 원래 값으로 돌아가지 않았습니다. Chromium은 8회 이후 약 677~686MiB에서 움직였고, Edge는 약 632MiB까지 올랐다가 마지막 약 608MiB로 내려갔습니다. 첫 사용 시 할당 시점과 실행 편차가 있어 전후 차이를 절감량으로 해석하지 않습니다. 원본 수치는 `node_modules/.cache/cropclip-cancel-*.json`에 저장했습니다.

반복 취소 검사는 다음과 같이 별도로 실행합니다. 횟수를 늘릴 때는 `CROPCLIP_PROFILE_CYCLES`에 4의 배수를 지정합니다.

```powershell
$env:CROPCLIP_PROFILE_REPORT="$PWD\node_modules\.cache\cropclip-cancel.json"
$env:CROPCLIP_PROFILE_CANCEL='1'
npx playwright test recording-profile
Remove-Item Env:CROPCLIP_PROFILE_CANCEL, Env:CROPCLIP_PROFILE_REPORT
```

## 일반 검사와 저장 종료 비교 재현

일반 검사는 `npm run check`로 실행합니다. 자원 비교는 Windows PowerShell에서 별도로 실행합니다.

```powershell
$env:CROPCLIP_PROFILE_REPORT="$PWD\node_modules\.cache\cropclip-profile.json"
npx playwright test recording-profile
Remove-Item Env:CROPCLIP_PROFILE_REPORT
```

`CROPCLIP_TEST_BROWSER=msedge`로 설치된 Edge를 선택하고, `CROPCLIP_TEST_EXTENSION_DIR`로 별도 빌드한 이전 버전의 dist 경로를 지정할 수 있습니다. 비교 실행은 동시에 돌리지 않습니다. 첫 실행에서 캐시한 `node_modules/.cache/cropclip-profile-source.webm`을 두 버전에 동일하게 사용합니다.

원본 측정 JSON은 `node_modules/.cache/cropclip-profile-fixed-{baseline,current}-{chromium,msedge}.json` 및 `cropclip-profile-repeat-{baseline,current}-chromium.json`에 저장했습니다. 캐시 파일은 Git에 포함하지 않습니다. 수치는 이 문서에 보존합니다.
