# 0.4.0 전체 점검

2026-11-14. 실행 코드, 설정·빌드·배포 흐름과 검사 결과를 정리했다. 이전 배포 태그는 v0.3.13이며, 방송 원본 저장을 포함한 다음 릴리스는 v0.4.0이다.

## 수정한 항목

- 저장 파일명에 붙이던 `_방송원본`을 제거했다. 자동·수동 다운로드 모두 저장된 기본 파일명을 사용한다.
- 녹화 대기 중에는 타이머에 ‘시작 중’을 표시한다. 화면 녹화 시작 신호부터 시간을 세고, 같은 시점의 재생 위치로 방송 원본을 조회한다. 조회에 실패하거나 조회 중 정지하면 보관해 둔 화면 녹화를 저장한다. 원본을 찾으면 화면 녹화를 해제하고 시작 시각을 이어받는다. 용량 표시를 켜면 현재 경로의 누적 크기를 표시한다. 하단 타이머의 글자색은 플레이어를 따른다.
- 방송 원본 MP4는 재생 범위의 끝을 요청 길이에 가깝게 맞춘다. 영상·음성 데이터와 시작 위치를 유지하고, 앞부분의 재생 정보만 바꾼다.
- 영역 좌표 계산에 영상의 퍼센트·픽셀 위치를 반영한다.
- 변환 엔진에 입력 파일 전체를 복사하던 과정을 Blob 읽기 마운트로 바꿨다. 성공·실패 시 마운트를 해제하고 작업 종료 시 변환 워커를 종료한다. 저장된 녹화 데이터와 녹화 제한은 이 변경으로 삭제·축소되지 않는다.
- 변환 결과는 워커 안에서 최대 4 MiB씩 읽어 Blob으로 전달한다. 결과창에서 출력 전체를 담는 배열을 한 번 더 만드는 경로를 제거했다.
- 입력이 64 MiB 이상인 원본 MP4의 출력은 브라우저 전용 임시 파일에 쓴다. 임시 파일 이름을 하나로 고정하고 동시에 덮어쓰지 않도록 잠근다.
- 대용량 원본 MP4는 임시 파일에서 바로 IndexedDB에 저장한 뒤 저장된 결과를 미리보기에 연다. FFmpeg가 출력 전체를 다시 읽어 Blob으로 만드는 단계를 건너뛴다.
- 방송 원본과 64 MiB 이상 결과는 결과창을 열 때 썸네일용 영상을 따로 디코딩하지 않는다. ‘장면 미리보기’를 누를 때만 생성하며, 종료 중이면 영상 읽기와 탐색을 취소하고 재생기·캔버스·URL을 해제한다.
- 결과창이 닫히면 준비 중이거나 변환 중인 워커를 즉시 종료한다. 실시간 변환과 재생기도 중단하고 결과창이 들고 있던 녹화·분할 파일 참조를 해제한다. 저장된 녹화와 임시 분할 파일의 삭제 유예는 유지한다.
- 일반 녹화의 시간·용량 분할은 결과창에 이미 열려 있는 영상의 실제 길이를 재사용한다. 미리보기에서 길이를 읽지 못했을 때만 별도 영상으로 확인한다.
- 64 MiB 이상 일반 녹화의 빠른 MP4 분할은 출력 조각을 브라우저 전용 임시 파일에 직접 쓰고, 개별·일괄 다운로드에서 그 파일을 사용한다. 임시 조각은 분할 결과를 다시 만들거나 녹화의 삭제 유예가 끝날 때 정리한다.
- 같은 디스크 출력 경로를 대용량 WebM 분할, 배속, 구간·형식 변환, 초반 끊김 정리와 WebM 탐색 정보 생성에도 적용했다. 실시간 변환은 조각을 순서대로 디스크에 쓰며, 다운로드 완료를 확인한 뒤 임시 파일을 삭제한다.
- 원본 MP4, WebM 탐색 정보, 초반 끊김 보정 결과의 저장 코드를 하나로 합쳤다. 임시 파일을 지우기 전에 해당 결과만 IndexedDB에서 다시 열어, 같은 녹화의 다른 파일까지 다시 읽는 작업을 줄였다.
- 전체 녹화 첫 2.5초에 시작한 끊김은 프레임이 재개된 시각까지 저장 파일 보정에 반영한다. 프레임 전달 큐가 막혀 건너뛴 프레임은 성공한 것으로 기록하지 않는다. 가까운 키프레임이 없으면 MP4는 편집 목록으로 시작점을 보정하고 WebM은 새 시작 프레임이 생기도록 변환한다. 보정할 만큼 정상 구간이 짧으면 자동 다운로드 대신 원본 확인 화면을 연다.
- 각 탭에서 처음 저장되는 H.264 전체 화면 녹화는 첫 5초의 영상 타임스탬프를 확인한다. 녹화 중 끊김이 감지되지 않았어도, 긴 공백이나 짧은 공백이 연속된 뒤 정상 간격으로 돌아오면 그 시점부터 재생되도록 보정한다.
- 녹화를 취소하면 대기열을 비우고 이미 진행 중인 저장 조각 변환도 즉시 중단한다.
- 대용량 원본의 임시 저장소가 차단되면 메모리 방식으로 재시도하지 않는다. 원본을 보존하고 결과창에서 MP4 재시도 또는 방송 조각 `.fmp4` 백업을 제공한다.
- WebM 분할 경계가 키프레임이 아닐 때 첫 화면이 멈추는 문제를 재인코딩으로 처리했다. MP4 빠른 분할은 재인코딩 없이 유지한다. WebM 분할에는 추가 처리 시간이 필요하다.
- 실제 녹화의 스테레오 음성을 WebM 분할용 Opus로 변환하면 엔진이 메모리 접근 오류로 종료되는 문제를 재현했다. Vorbis로 변환해 두 채널을 유지하며, 분할 파일의 영상·양쪽 음성을 검사한다.
- 일부 MediaRecorder WebM이 1,000fps로 해석돼 변환 중 중복 프레임을 대량 생성하던 문제를 확인했다. WebM 분할·구간 변환·배속 저장·GIF는 실제 프레임 시각을 유지하도록 바꿨다.
- 일반 WebM 자동 다운로드는 편집용 탐색 정보 생성을 건너뛴다. 결과창 로딩 중 누른 다운로드는 준비가 끝난 뒤 결과창과 같은 파일을 받는다. 자동 다운로드 실패 시에는 결과창에서 재시도할 수 있다.
- 결과 준비가 끝나기 전에 일반 다운로드·분할·변환 버튼이 실행되지 않도록 잠근다. 준비 화면의 다운로드 예약은 사용할 수 있다.
- 방송 원본 저장 알림을 ‘원본 저장 중’으로 줄였다. 화면 녹화 전환 알림은 형식과 이유를 두 줄로 표시한다.
- 완료를 기다리는 다운로드의 기록이 사라지면 다음 파일을 시작하기 전에 실패를 알리고 다운로드 URL과 리스너를 해제한다.
- 일반 녹화의 브라우저 종료 이벤트가 5초 동안 도착하지 않으면 전달된 영상으로 저장을 마무리한다. Edge에서 종료 이벤트를 누락시켜 결과창과 재생을 확인했다.
- 녹화 조각 저장 응답이 15초 동안 오지 않으면 디스크에 기록된 연속 구간을 복구한다. 복구가 성공하면 일반 정지와 동일하게 완료 처리한다.
- 최종 저장 응답 대기를 30초로 제한한다. 응답이 사라져도 이미 저장된 녹화 ID를 확인해 완료 처리한다. Edge에서 최종 응답을 누락시켜 실패 경고 없이 결과창이 하나만 열리고 녹화 버튼이 풀리는 것을 확인했다.
- 팝업과 플레이어 타이머를 ‘용량 · 시간’ 순서로 통일하고 숫자 폭을 일정하게 맞췄다.
- 영역 테두리와 실제 영상의 배율이 어긋나는 `object-fit: cover`, `none`, `scale-down` 계산을 수정했다. 테두리는 실제 플레이어 표시 범위 안으로 제한한다.
- 단축키 설정창의 Tab·Enter·Escape 조작을 복구했다. 사용자가 숫자에 지정한 녹화 단축키를 기본 영역 전환보다 우선한다.
- 원본 응답의 크기 헤더가 없더라도 읽는 도중 용량 한도를 적용하고, 잘못된 재생 목록의 무한대 길이를 거부한다.
- 원본 첫 조각을 저장 큐에 전달하면 녹화 쪽 참조를 해제하고, 보관한 마지막 조각도 사용 후 비운다. 화면 캡처 준비에 실패하면 캔버스의 메모리도 즉시 비운다.
- 임시 영상 삭제는 영상 데이터를 읽지 않고 저장 키만 순회한다. Edge 삭제 재시도 검사에서 영상 값을 읽는 호출이 4회에서 0회로 줄었다.
- 원본 탐색 중 영상 버퍼 갱신이 끝난 뒤에도 재생 시각을 대조한다. 재생 목록에 방송 시각 태그가 끼어 있어도 해당 영상 조각을 건너뛰지 않는다.
- 취소 직후 원본을 다시 탐색해도 앞선 탐색의 영상 버퍼 감시가 겹쳐 남지 않도록 했다. 종료한 탐색은 리스너와 영상 참조를 해제한다.
- 원본 녹화 정지 후 마지막 방송 조각을 최대 3초 기다린다. 방송 서버가 지연되면 받은 구간까지 저장하고 안내한다. Edge에서 목록 응답을 멈춘 상태로 검사했을 때 약 3.1초 뒤 결과창이 열렸고, 받은 6.48초 구간이 재생됐다.
- 분할 파일 번호를 숫자로 정렬한다. 1,000개 이상에서도 번호와 실제 구간이 뒤바뀌지 않는다.
- 녹화와 결과창에 중복된 코덱 우선순위를 공통 상수로 합쳤다. 프레임 이동 간격은 현재 설정 대신 해당 녹화의 저장된 프레임 설정을 따른다.
- 잘못 중첩된 설정 라벨, 누락된 타이머 색상, 의미 없이 통과하던 검사 조건을 정리했다.
- 크롬 웹스토어 자동 업로드 작업을 제거했다. GitHub 빌드·릴리스는 유지하며, 재지정된 태그의 이전 빌드가 릴리스를 덮어쓰지 않도록 확인한다.
- README의 지원하지 않는 이미지 복사 설명과 배포물에 불필요한 SVG를 제거했다. 개인정보처리방침에 원본 조각 요청을 반영했다.

## 남은 항목

### 배포 전

- [ ] 최신 0.4.0 빌드로 GitHub 전체 검사를 실행한다. 같은 빌드의 로컬 단위 검사와 기본 Chromium 전체 검사는 통과했다.
- [ ] Chrome과 Edge에서 실제 치지직 방송으로 원본 탐색 성공·실패와 녹화 중 검색 이동을 확인한다. 일반 화면 녹화는 33초 전후로 반복하고 정지·취소·결과창 닫기를 각각 확인한다.
- [ ] **전체 녹화 시작 시 방송 재생 지연.** Edge 1080p 샘플에서 첫 녹화의 최대 프레임 간격은 기본 H.264 약 380ms, H.264 캔버스 약 310ms, VP8 약 140ms였다. 각각 별도 실행 1회이며, 실제 치지직에서 반복 측정하고 빠른 MP4 변환을 유지할 수 있는 후보를 비교한다.
- [ ] **우선 1 — 장시간 잔류 메모리 추적.** 대용량 원본의 전체 다시 읽기를 제거했다. 반복 측정에서 남은 증가분은 대부분 GPU 프로세스에서 나왔다. 실제 치지직에서 같은 탭을 유지하고 녹화·저장·취소를 더 오래 반복해 GPU 메모리를 추적한다.
- [ ] **우선 2 — 실제 저장 공간과 메모리 부족.** 실패 주입과 결과창 닫기 복구는 로컬에서 확인했다. 여유 공간이 적은 환경의 실제 쓰기 실패와 브라우저가 메모리 부족으로 강제 종료된 뒤의 복구는 별도 확인이 필요하다.
- [ ] 배포할 커밋의 버전과 ZIP을 확인한 뒤 v0.4.0 태그로 GitHub 빌드를 실행한다. 크롬 웹스토어 제출은 수동으로 진행한다.

## 검증 범위

- 출력 전달 변경 뒤 동일 샘플에서 변환 전 536 MiB, 변환 중 표본 최고 1,464 MiB, 미리보기 822 MiB, 닫은 3초 뒤 824 MiB를 측정했다. 300초 MP4의 299초 위치를 재생했고, 워커에서 배열과 Blob으로 각각 읽은 테스트 MP4의 바이트가 일치했다.
- 임시 디스크 출력 적용 뒤 315MB 샘플의 첫 측정에서 최고 973 MiB, 결과창을 닫은 3초 뒤 815 MiB를 기록했다. Edge·Chromium에서 임시 디스크와 메모리 방식의 MP4가 바이트 단위로 일치했다.
- 최종 빌드의 315MB 샘플에서 디스크 출력 사용과 임시 파일 삭제를 직접 확인했다. 시작 532 MiB, 표본 최고 1,047 MiB, 결과창을 닫은 3초 뒤 490 MiB였다. 종료 뒤 수치는 실행마다 달라 장시간 누수 판정에는 반복 측정이 필요하다.
- 같은 Edge 실행에서 315MB 테스트 원본을 새 결과창으로 3회 저장했다. 결과창을 닫은 30초 뒤 프로세스 전용 메모리 합계는 445 → 455 → 467 MiB, GPU는 219 → 223 → 232 MiB였다. 매회 300초 MP4의 299초 지점이 재생됐고, 변환 워커와 임시 출력 파일은 남지 않았다. 녹화 조각의 예약 삭제 전 측정이며, 3회 표본으로 증가 원인을 구분할 수 없다.
- 출력 전체 재읽기 제거 후 동일한 315MB 테스트를 3회 반복했다. 결과창을 닫은 30초 뒤 전체는 472 → 614 → 619 MiB, GPU는 239 → 381 → 384 MiB, GPU를 뺀 수치는 233 → 233 → 235 MiB였다. 3회 모두 299초 지점에서 재생됐고 임시 파일 및 변환 워커는 남지 않았다. 전체 메모리 절감은 이 실행에서 확인되지 않았다. 브라우저 회차별 GPU 차이와 장시간 누수 여부는 별도 확인이 필요하다.
- 같은 315MB 원본으로 썸네일 변경 전후를 Edge에서 3회씩 순차 측정했다. 변환 후 영상 소스를 연 요소가 2개에서 1개로 줄었다. 창을 닫은 30초 뒤 GPU는 변경 전 234 → 229 → 228 MiB, 변경 후 225 → 231 → 234 MiB였다. 전체는 변경 전 475 → 466 → 473 MiB, 변경 후 455 → 469 → 472 MiB였다. 양쪽 모두 299초 지점에서 재생됐다. 자동 썸네일로 인한 추가 디코딩은 재현했지만, 이전 실행의 380 MiB대 GPU 점유는 이번 비교에서 재현되지 않았다.
- 변환 응답을 멈추고 결과창 종료 이벤트를 재현했을 때 기존에는 워커가 1개 남았고 수정 후 0개가 됐다. 다시 열면 원본을 저장할 수 있었다. 315MB 정상 저장 후 창을 닫은 30초 뒤 3회 측정에서 전용 메모리 합계는 453 → 469 → 472 MiB, GPU 프로세스는 220 → 231 → 233 MiB였다. 매회 파일의 299초 지점이 재생됐고 워커와 임시 출력 파일은 남지 않았다. 정상 완료 뒤 잔류량은 이전 썸네일 변경 결과와 비슷했다.
- Edge와 Chromium의 64 MiB 이상 테스트 원본에서 임시 저장소 접근·마운트 실패, 변환 실패, 임시 파일을 연 뒤 결과창 닫기를 재현했다. 원본이 보존됐고 저장소 실패 때 `.fmp4` 백업을 받았다. 다시 열었을 때 3초 MP4가 재생됐고 임시 파일이 정리됐다. 별도 단위 검사로 디스크 쓰기 예외와 일부 바이트만 기록된 경우를 확인했다.
- 0.4.0의 1080p·33초 전체 녹화를 4회씩 반복했다. 정리 수정 전 프로세스 전용 메모리는 814 → 729 → 739 → 640 MiB, 수정 후에는 830 → 700 → 751 → 754 MiB였다. 매회 결과창을 닫은 뒤 열린 프레임과 변환 워커는 0개였고, 마지막 정리 후 녹화기·캔버스·생성 트랙도 0개였다. 이 표본에서는 프로세스 메모리 절감량이나 장시간 누수 여부를 확정할 수 없다.
- 전체 녹화 시작·취소 8회 뒤 임시 녹화 데이터, 열린 프레임, 녹화기와 변환 워커는 0개였다. 원본 방송 저장·재생과 삭제 재시도·브라우저 재시작 복구도 통과했다.
- 현재 빌드에서 Edge 전체 녹화 취소를 8회 반복한 검사와 1080p·33초 정지를 4회 반복한 검사가 모두 통과했다. 정지 후 결과창을 닫은 시점의 전용 메모리는 838 → 745 → 752 → 738 MiB였다. 매회 열린 프레임과 변환 워커는 0개였고, 마지막 확인에서 녹화기·캔버스·생성 트랙도 0개였다.
- 일반 결과에서 미리보기가 로드된 뒤 분할할 때 별도 영상 요소가 1개 열리는 것을 재현했다. 수정 후 Edge에서 WebM→MP4 2·3·4분할, 구간 지정, 용량 기준 재시도 모두 추가 영상 요소가 0개였고 결과가 재생됐다. 정지 중 캡처 해제, 자동 저장 실패 복구, 미니 플레이어 이동 검사도 통과했다.
- 같은 315MB·302초 MP4를 Edge에서 빠른 4분할로 한 번씩 비교했다. 메모리 출력 → 디스크 출력에서 프로세스 전용 메모리 표본 최고는 1,479 → 1,153 MiB, 결과창을 닫은 5초 뒤는 1,021 → 465 MiB였다. 두 방식의 5초 뒤 GPU는 247 → 238 MiB였다. 분할 처리 시간은 약 19.8 → 14.9초였으며 실행별 편차는 별도 확인이 필요하다. Edge·Chromium에서 개별 다운로드, 출력 실패 뒤 재시도, 구간 변경 및 녹화 삭제 시 임시 파일 정리를 확인했다.
- 동일한 315MB MP4의 첫 33초를 Edge에서 WebM으로 3분할했다. 메모리 출력 → 디스크 출력에서 표본 최고는 1,152 → 964 MiB, 소요 시간은 22.9 → 22.4초, 결과창을 닫은 5초 뒤는 721 → 723 MiB였다. 각각 1회 측정이다. Edge·Chromium에서 대용량 분할, 2배속, 강제 빠른 변환 실패 뒤 실시간 변환, 초반 정리, WebM 탐색 정보 생성과 임시 파일 정리를 확인했다.
- 초반 2.5초 경계에서 정상 프레임은 자르지 않고, 경계를 걸쳐 건너뛴 프레임은 보정하는 회귀 검사가 통과했다. Edge에서 주입한 초반 끊김이 H.264 WebM·MP4의 저장 파일에서 제외됐고, 짧은 녹화는 보존됐다. 128 MiB 초과 샘플의 보정도 통과했다. 기본 H.264 방송 재생 검사에서는 가장 긴 프레임 간격이 클릭 약 0.59초 뒤에 끝났고, 첫 저장 조각은 약 1.11초에 도착했다.
- Chromium에서도 H.264 WebM·MP4의 초반 끊김 보정과 128 MiB 초과 파일 검사를 통과했다. 실제 치지직 방송에서는 Edge로 32.7초 원본 MP4를 저장해 미리보기 로드를 확인했다. 이 라이브 시도는 시작 직후의 프레임 표본을 수집하지 못해 방송 끊김을 판정하는 데 사용하지 않았다.
- Edge 1080p 로컬 샘플 재검사에서 기본 H.264 첫 녹화 프레임 간격은 약 230~260ms였다. 실제 영상 크기 사전 확인 210ms, 키프레임 옵션 제거 250ms, 모션 힌트 260ms, 초반 프레임 전달 간격 확대 240ms로 모두 200ms 기준을 넘었다. 원본 영상 트랙을 직접 넘긴 실험에서는 2초 안에 첫 저장 조각이 오지 않았다. 별도 워커의 WebCodecs H.264 실험은 영상 인코딩만 했고 첫 최대 간격은 약 290ms였다. 실험 변경은 제품에 적용하지 않았다.
- 첫 1초가 정지 장면이고 뒤쪽에 가까운 키프레임이 없는 H.264 WebM·MP4를 준비했다. 수정 전에는 2.3초 원본이 그대로 내려받아졌다. 수정 후 Edge와 Chromium에서 다운로드 파일을 직접 열어 정지 장면이 없고 0.35초 시점에 그림이 변하는지 확인했다. 보정할 정상 구간이 0.5초 미만인 샘플은 자동 저장 대신 원본 확인 화면에 남았다.
- 녹화 중 감지 표시가 없는 샘플도 확인했다. WebM은 1초 영상 프레임 공백, MP4는 약 100ms 간격이 여러 번 이어지는 초반을 주입했다. 첫 파일 검사에서 둘 다 복구 지점을 찾았고 다운로드 파일은 움직이는 구간부터 재생됐다. 실제 H.264 WebM·MP4 테스트에서는 한 탭의 첫 저장 파일에서만 추가 검사가 실행됐다.
- Edge의 로컬 HLS 샘플에서 원본 조회 성공 후에도 타이머 시작 시각이 같았고, 요청 구간 약 4.54초는 4.57초 MP4로 저장됐다. 파일명 접미사 제거도 다운로드에서 확인했다.
- 실제 치지직 장시간 방송의 메모리와 GPU 사용량은 추가 확인이 필요하다.
